# Session 08 — أنظمة البث اللحظي والتخزين في الذاكرة (Redis & Real-Time Systems)

## Objective
إتقان التفكير في أنظمة البث اللحظي (Real-Time Systems)، والتفريق بين بروتوكول النقل (Transport)، والتخزين الموقت في الذاكرة (Transient State)، والربط عبر السيرفرات المتعددة (Cross-Server Fan-Out)، واختيار المعمارية المناسبة لمتابعة موقع الكباتن وتحديثات اللوحة بناءً على معدل التغيير وحداثة البيانات والسلامة، دون التحيّز لتقنية محددة أو اعتبار Redis إجبارياً لكل نظام.

## Why This Matters to HDS
البث اللحظي لموقع الكباتن وتحديثات لوحة التجّار يتطلب معمارية تفصل بين **الموقع الآني المؤقت (Latest Location State)** وبين **البيانات الدائمة المعتمدة (Durable Business Data)**. إذا عوملت كل إشارة موقع متكررة كـ معاملة كتابة دائمة على الداتا بيز الرئيسية بنفس الأسلوب، فإن ذلك يخلق تضخماً متزايداً في عمليات الكتابة، مما يحتم تصميم المعمارية بناءً على طبيعة البيانات ودورة حياتها.

## In Scope
* **معيار اختيار معمارية البث اللحظي (Realtime Decision Framework):** تحديد البيانات الفورية مقابل البيانات الدائمة، معدل التحديث، والجهة المستفيدة.
* **التفريق الحاسمي بين الأركان الثلاثة للنظام اللحظي:**
  - **بروتوكول النقل (Transport):** الاتصال المستمر bidirectional (مثل WebSockets أو SSE).
  - **التخزين المؤقت بالذاكرة (Transient State):** حفظ أحدث موقع للكابتن (مثل Redis Data Store).
  - **النشر المتعدد عبر السيرفرات (Cross-Server Fan-Out):** ربط السيرفرات عند التوسع الأفقي (مثل Redis Pub/Sub).
* **الفارق الجوهري بين التخزين بالذاكرة والتمرير:**
  - `Redis Data Store` ("أين أحدث موقع للكابتن الآن؟").
  - `Redis Pub/Sub` ("من المتصل حالياً ويريد استلام التحديث فوراً؟").
  - **التنبيه الحاسمي:** `Redis Pub/Sub ≠ Durable Queue` (الـ Pub/Sub ليس طابوراً دائماً؛ والرسائل لا تحفظ للمقطوعين).
* **الموقع اللحظي المؤقت مقابل التاريخ الجغرافي الدائم (Latest Location vs Location History).**
* **مفهوم الحداثة وجفاف البيانات (Freshness, TTL & Stale Data):** التمييز بين البيانات الطازجة والبيانات القديمة.
* **ترتيب الرسائل المتأخرة عبر الشبكة (Out-of-Order Updates):** حماية الموقع من التراجع بسبب تأخر الحزم.
* **إعادة الاتصال واستعادة الحالة (Reconnection & Latest State Sync).**
* **قائمة أسئلة اتخاذ القرار الأمني والمعماري للأنظمة اللحظية.**

## Out of Scope
* تفاصيل سياسات تفريغ الذاكرة بـ Redis (Memory Eviction Policies / LRU internals).
* تفاصيل عقد وبروتوكولات الـ Redis Cluster و Sentinel consensus nodes.
* الشفرات التفصيلية لضغط حزم بروتوكول WebSockets (Frame compression & TCP tuning).
* قواعد البيانات الزمنية التفصيلية (Time-Series DB internals).

## Mental Model

### النموذج الذهني المعماري لفصل البث عن التخزين الدائم:
```text
تطبيق الكابتن (Driver App)
     │ (بث الموقع الحي عبر WebSocket)
     ▼
[بوابة البث اللحظي Realtime Gateway]
     │
     ├───► [تخزين الموقع الأخير بـ Redis RAM] ──► (حفظ أحدث موقع: SET driver:44:loc)
     │                                                     │
     ├───► [بث عبر Redis Pub/Sub Broker]                   ▼
     │              │                              (الموقع الأخير اللحظي)
     │              ▼
     │     [مستقبل عبر خوادم متعددة] ──► [تطبيقات العملاء] (تحديث الخريطة فوراً)
     │
     └─► [التخزين الدائم للسجلات المعتمدة] ──► [PostgreSQL / Spatial History]
```

## Learning Path

### 1. ما الذي يجعل النظام لحظياً؟ (What Makes a System Realtime?)
* النظام اللحظي لا يعني حفظ كل نقطة للابد، بل يعنى **توصيل البيانات الحديثة جداً بـ أدنى زمن تأخير (Low Latency)** للطرف المستفيد.

---

### 2. التفكيك الصريح للأركان الثلاثة
* **بروتوكول النقل (Transport):** بروتوكول WebSockets يقيم اتصالان دائمين ثنائي الاتجاه بين العميل والخادم، بخلاف الـ HTTP القائم على طلب واستجابة (Request/Response).
* **التخزين المؤقت بالذاكرة (Transient State Store):** التخزين بالذاكرة (مثل Redis) يوفر وصولاً منخفض التكلفة جداً للبيانات المؤقتة سريعة التغير.
* **البث المتعدد عبر الخوادم (Cross-Server Fan-Out):** عند التوسع الأفقي لـ خوادم WebSockets (سيرفر أ وسيرفر ب)، يربط الـ Redis Pub/Sub التحديثات ليتم البث للعميل بغض النظر عن السيرفر المتصل به.

---

### 3. الفارق الحاسمي: Redis Data Store مقابل Redis Pub/Sub
* `Redis Data Store` (`SET driver:44:loc`): يحفظ آخر موقع معروف حتى لو لم يكن هناك عميل يشاهده الآن.
* `Redis Pub/Sub` (`PUBLISH driver_channel`): يبث الإشارة تزامناً للمستمعين المتصلين **حالياً فقط**.
* ⚠️ **تنبيه مهندسي حاسم:** الـ Pub/Sub ليس طابوراً دائماً (Durable Queue)؛ لو كان المستمع غير متصل لحظة البث، فإنه **لن يتلقى الرسالة الفائتة** عبر Pub/Sub بمفرده، مما يحتم وجود آلية يجلب بها أحدث موقع مخزن عند إعادة الاتصال!

---

### 4. الموقع اللحظي المباشر مقابل السجل الجغرافي التاريخي
* **الموقع اللحظي (Latest Location):** يجيب عن *"أين الكابتن الآن؟"* (مرشح ممتاز للذاكرة المؤقتة).
* **السجل الجغرافي (Location History):** يجيب عن *"أين تحرك الكابتن خلال الـ 30 دقيقة الماضية؟"* (مرشح للتخزين العلاقي الدائم بـ PostgreSQL/PostGIS أو مخزن زمني).

---

### 5. حداثة البيانات وجفاف الموقع (Freshness, TTL & Stale Data)
* البيانات الجغرافية لها صلاحية زمانية؛ موقع الكابتن قبل 3 ثوانٍ هو موقع طازج (Fresh)، أما الموقع قبل 90 ثانية فيعتبر موقعاً قديماً أو جافاً (Stale Data).
* تُدار حداثة البيانات بمهلة انتهاء صلاحية (TTL) أو بمقارنة الطابع الزمني (Timestamp).

---

### 6. الوصول غير المرتب للحزم عبر الشبكة (Out-of-Order Updates)
* بسبب تقلبات شبكات الموبايل، قد تصل حزمة موقع قديمة (تأخير 10 ثوانٍ) بعد وصول حزمة أحدث.
* الـ Backend يجب ألا يحدث الداتا ببيانات قديمة، بل ينظر للطابع الزمني للحدث (`event_timestamp`) ويقبل التحديث الأحدث فقط.

---

### 7. التوسع الأفقي لخوادم WebSockets
* لو كان الكابتن متصلاً بـ `Server A` والعميل متصلاً بـ `Server C`؛ فإن `Server A` يمرر موقع الكابتن عبر `Redis Pub/Sub` إلى `Server C` والذي بدوره يدفعها عبر اتصال الـ WebSocket المفتوح للعميل.

## Real-World / HDS Examples
* **تتبع الكابتن المباشر (Live Tracking):** الكابتن يرسل موقعه كل 3 ثوانٍ. الـ Gateway يكتب أحدث موقع في Redis ويبث عبر Pub/Sub. العميل المتصل يرى الأيقونة تتحرك بمرونة. إذا فات العميل 3 نقاط بسبب انقطاع الشبكة، لا يتم إعادة تشغيل المسار بالكامل، بل يطلب العميل أحدث موقع مخزن فور إعادة الاتصال.
* **تحديثات لوحة التاجر (Merchant Dashboard Realtime Updates):** الأوردر المقبول أو الكابتن الواصل يحث حدثاً بالـ Backend؛ يتم بث التحديث عبر WebSocket للوحة المحل لتظهر إشارة إشعار صوتي فوري.

## Common Misconceptions
* *Misconception 1:* "الـ Redis Pub/Sub هو طابور رسائل دائم (Durable Queue)." -> *الواقع:* الـ Pub/Sub هو آلية بث تنبيهية تزامنية للمتصلين حالياً فقط، وإذا كان المستمع غير متصل تضيع الرسالة المبعوثة.
* *Misconception 2:* "استخدام WebSockets يعني ضمان وصول كل حزمة جغرافيّة للعميل." -> *الواقع:* الاتصال الدائم لا يعوض غياب استراتيجية استعادة أحدث موقع مخزن عند انقطاع الاتصال.
* *Misconception 3:* "Redis يجب أن يكون مصدر الحقيقة الرئيسي لأنه يعطي أحدث البيانات وسريع جداً." -> *الواقع:* الـ Redis في الغالب هو كاش أو مخزن مؤقت، والبيانات المالية والدائمة حقيقتها في الداتا بيز الدائمة (PostgreSQL).
* *Misconception 4:* "البث اللحظي يتطلب حفظ وتسجيل كل نقطة جغرافيّة للأبد." -> *الواقع:* البث اللحظي يهتم بحداثة الموقع المباشر، وحفظ السجلات التاريخية له متطلبات وأرشيف منفصل.

## Failure / Edge Cases
* **توقف سيرفر Redis عن العمل (Redis Outage):**
  الـ Redis يتعطل مؤقتاً ← النظام الأساسي للأوردرات والداتا بيز الدائمة يعمل بسلام، بينما تتراجع سرعة البث اللحظي أو تعود للمسارات البديلة دون ضياع بيانات الأوردرات المالية.
* **انقطاع اتصال العميل أثناء البث (Subscriber Disconnection):**
  العميل يفقد الشبكة لثوانٍ ← الـ Pub/Sub يبث الرسائل وتضيع على العميل؛ فور إعادة الاتصال بالـ WebSocket يجلب العميل أحدث موقع مخزن بـ `SET driver:44:loc` ويستأنف البث.
* **تعدد خوادم الـ WebSocket (Multi-Server Gateway):**
  الكابتن متصل بسيرفر 1 والعميل بسيرفر 3 ← يعبر الموقع عبر الـ Redis Pub/Sub بين السيرفرات ليظهر على خريطة العميل.
* **قدوم حزمة موقع قديمة متأخرة (Stale Out-of-Order Packet):**
  حزمة موقع قديمة تصل متأخرة ← السيرفر يفحص `event_timestamp` ويرفض التحديث للحفاظ على اتجاه الكابتن الصحيح.
