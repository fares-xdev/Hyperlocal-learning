# Session 02 — كيف يعمل الـ Backend في تطبيقات الويب؟ (Web Backend & HTTP APIs)

## Objective
فهم دورة الحياة المفاهيمية للطلب والاستجابة (Conceptual Request/Response Lifecycle) الكاملة بين تطبيقات العميل (PWA, Merchant Portal, Driver App) والـ Backend، والتفريق الحاسمي بين المصادقة (AuthN) والتفويض (AuthZ) والتحقق (Validation)، ومعرفة معنى بروتوكول HTTP وأكواد الاستجابة دون الغرق في كود الـ Syntax أو تفاصيل المكتبات.

## Why This Matters to HDS
في المنصات الهندسية، لا يجوز التعامل مع الـ Backend كـ "صندوق أسود" أو "اختصار مباشر للداتا بيز". يجب على مهندس البرمجيات فهم **كيف تسافر الأوامر عبر الشبكة**، وكيف يتحقق الـ Backend من هوية وصلاحية الداعي، ولماذا يُمنع منعاً باتاً الوثوق في بيانات الواجهة الأمامية (Client Data).

## In Scope
* **المسار المفاهيمي لـ Request/Response Lifecycle:** (العميل ← واجهة الـ API ← التوجيه Routing ← المصادقة AuthN ← التفويض AuthZ ← التحقق Validation ← منطق العمل Business Logic ← عمليات الداتا بيز DB Operations ← استجابة الـ HTTP).
* **مسؤوليات العميل مقابل الخادم (Client vs Backend Responsibilities).**
* **تشريح الـ HTTP Request:** الطرق (GET, POST, PATCH, DELETE)، المسارات (Paths)، البيانات الوصفية (Headers)، وحمولة البيانات (Body Payload).
* **التفريق بين المصادقة والتفويض:**
  * **المصادقة (AuthN):** "من أنت؟" (التحقق من الهوية من خلال الـ Bearer Token).
  * **التفويض (AuthZ):** "هل يملك هذا المستخدم الموثق الصلاحية لتنفيذ هذا الفعل على هذا المورد بالتحديد؟".
* **مفهوم "الطلب ≠ العملية التجارية الواحدة" (Request ≠ Business Operation):** قد يطلق طلب HTTP واحد مجموعة من الإجراءات والتحققات الداخلية.
* **اتفاقية دلالات أكواد الـ HTTP (Status Code Conventions):**
  * `200 OK` / `201 Created` للنجاح.
  * `401 Unauthorized` (الهوية غير معروفة/مفقودة).
  * `403 Forbidden` (الهوية معروفة ولكن الوصول غير مصرح).
  * `404 Not Found` (المورد غير موجود).
  * `400` / `422` (أخطاء الطلب أو مخالفة قواعد العمل وفق اتفاقية الكورس).
  * `500 Internal Server Error` (خطأ غير متوقع بالخادم).

## Out of Scope
* تفاصيل بروتوكولات HTTP/2 أو HTTP/3 الداخلية.
* بروتوكولات gRPC أو الشبكات الثنائية Binary Protocols.
* معمارية وأكواد الـ API Gateway المتقدمة (سيتم طرحها لاحقاً كخيار معماري).
* تفاصيل تشفير الـ JWT الترسيمية (مخصصة للجلسة 05).
* تفاصيل معاملات الداتا بيز المعقدة DB Transactions (مخصصة للجلسة 04).

## Mental Model

### دورة الحياة المفاهيمية للطلب (Conceptual Request Lifecycle):
```text
تطبيق العميل (Client App: PWA / Mobile)
     │ (إرسال HTTP Request مع Bearer Token)
     ▼
[الـ Backend API الخاصة بـ HDS]
     │
     ├─► [1. التوجيه Routing] ──────────► (توجيه المسار للخدمة المعنية)
     │
     ├─► [2. المصادقة AuthN] ─────────► (من أنت؟ ──فشل──► 401 Unauthorized)
     │
     ├─► [3. التفويض AuthZ] ──────────► (هل مسموح لك بهذا المورد؟ ──فشل──► 403 Forbidden)
     │
     ├─► [4. التحقق Validation] ──────► (هل شكل البيانات سليم؟ ──فشل──► 400/422)
     │
     ├─► [5. منطق العمل Business Logic] (تطبيق قواعد المنظومة والحسابات)
     │
     └─► [6. عمليات الداتا بيز DB Ops] ─► (قراءة/كتابة البيانات المطلوبة)
                                                │
   استجابة HTTP مناسبة (مثل 201 Created) ◄──────┘
```

## Learning Path

### 1. ماذا يحدث عندما يضغط العميل زراً في الواجهة؟ (What happens when I click a button?)
* التفاعل بالواجهة يولد **HTTP Request** يخرج عبر الشبكة يحمل عنوان المسار، التوكن، والبيانات.

---

### 2. مسؤوليات العميل مقابل الـ Backend (Client vs Backend)
* **تطبيق العميل (Client):** يعرض الواجهة، يتلقى المدخلات، ويطلب تنفيذ الأوامر. لا يملك أي سلطة أمنية ولا يُؤتمن على الأسعار أو القواعد.
* **الـ Backend:** المحرك الأساسي لحماية البيانات، وتطبيق قواعد العمل، والتحقق من الهوية والصلاحيات، وإدارة التخزين.

---

### 3. ما هو بروتوكول HTTP وتشريح الـ Request والـ Response؟
* **تشريح الطلب (Request Anatomy):**
  * **الطريقة (Method):** `GET` (قراءة آمنة)، `POST` (إنشاء)، `PATCH`/`PUT` (تعديل)، `DELETE` (حذف).
  * **Headers:** بيانات وصفية، مثل `Content-Type: application/json` ورمز التوثيق `Authorization: Bearer <token>`.
  * **توضيح الـ Bearer Token:** التوكن هو وثيقة اعتماد (Credential) يرسلها العميل، ويفحصها الـ Backend للتحقق من هوية صاحب الطلب بدقة.
  * **Body (Payload):** البيانات المبعوثة بصيغة JSON.
* **تشريح الاستجابة (Response Anatomy):**
  * **Status Code:** رقم دلالي يعبر عن نتيجة الطلب.
  * **Response Body:** البيانات المرتجعة أو تفاصيل الخطأ.

---

### 4. التمييز الحاسمي بين المصادقة والتفويض (AuthN vs AuthZ)
* **المصادقة (Authentication - AuthN):** *"من الذي يرسل هذا الطلب؟"* (تتم عبر فحص الـ Bearer token). إذا فشلت ← نرجع `401 Unauthorized` ("لا نعرف من أنت").
* **التفويض (Authorization - AuthZ):** *"هل هذا المستخدم الموثق مسموح له بتنفيذ هذا الفعل على هذا المورد المحدد؟"*.
  * **مثال HDS:** الكابتن (أ) موثق بنجاح (AuthN passed)، لكنه يحاول تعديل توصيل الكابتن (ب). هنا تنجح المصادقة وتفشل الصلاحية ← نرجع `403 Forbidden` ("نعرف من أنت ولكن لا تملك الصلاحية").

---

### 5. التحقق، منطق العمل، وعمليات الداتا بيز
* **التحقق (Validation):** التأكد من أن الهيكل المبعوث يحتوي على الحقول المطلوبة وبقيم مقبولة شكلياً.
* **منطق العمل (Business Logic):** تطبيق قوانين HDS (مثال: "فحص توافر الوجبة").
* **عمليات الداتا بيز (Database Operations):** التفاعل التخزيني. بعض العمليات المركبة تتطلب **معاملة داتا بيز (DB Transaction)** لضمان النجاح أو الفشل كاملاً ككتلة واحدة (سيتم فصلها بالجلسة 04).

---

### 6. مفهوم: "الطلب ≠ العملية التجارية الواحدة" (Request ≠ Business Operation)
* طلب HTTP واحد مثل `POST /api/v1/orders` ليس مجرد "أمر داتا بيز واحد"، بل هو **طلب قد يطلق عدة عمليات مفاهيمية داخلية**:
  `فحص السلة` → `التأكد من التوافر` → `حساب الإجمالي` → `إنشاء الأوردر` → `حجز المبلغ` → `إرسال التنبيهات`.

---

### 7. دلالات أكواد الأخطاء كـ اتفاقية (HTTP Status Conventions)
* الأنظمة التي تحترم دلالات HTTP ترفض إرجاع `200 OK` مع كائن خطأ داخلي (`{ error: true }`) كاستجابة وفيرة.
* في هذا الكورس، نعتمد اتفاقية دلالية مستمرة:
  * `400` / `422`: للبيانات غير الصالحة أو مخالفة القواعد.
  * `401`: لعدم وجود توكن أو تلفه.
  * `403`: لمنع الوصول للموارد غير المملوكة.
  * `404`: للموارد المفقودة.
  * `500`: للأخطاء الداخلية غير المتوقعة في الخادم.

## Real-World / HDS Examples
* **تأكيد الطلب (`POST /api/v1/orders`):** العميل يرسل السلة. الـ Backend يتحقق من الهوية (AuthN)، يضمن الصلاحية (AuthZ)، يفحص الشكليات (Validation)، يطبق قوانين السعر (Business Logic)، يحفظ البيانات (DB Operations)، ويرجع `201 Created`.
* **تحديث حالة التوصيل من الكابتن (`PATCH /api/v1/deliveries/101/status`):** الكابتن يرسل حالته الجديدة `OUT_FOR_DELIVERY`. الـ Backend يتحقق أولاً هل هذا الكابتن هو المخصص لـ Delivery 101 بالتحديد؟ (إذا لم يكن هو، يتم رفض الطلب بـ `403 Forbidden`).

## AI Interaction
* **توجيه الـ AI:** اطلب من الـ AI Agent: *"اشرح دورة حياة الطلب عندما يغير الكابتن حالة التوصيل لـ OUT_FOR_DELIVERY عبر API."*
* **التحدي والمراجعة:** افحص إجابة الـ AI: هل نسيت المصادقة؟ هل أهملت فحص ملكية الكابتن للأوردر (AuthZ)؟ وهل كتبت بالداتا بيز قبل التحقق؟ اطلب من الـ AI تصحيح الأخطاء.

## Common Misconceptions
* *Misconception 1:* "طالما الواجهة الأمامية تمنع العميل من الضغط على الزر، فالـ Backend لا يحتاج لفحص الصلاحية." -> *الواقع:* الواجهة تحت سيطرة المستخدم الكاملة ويمكن تجاوزها بسهولة بـ Postman أو curl؛ الـ Backend هو الجدار الأمني الحتمي.
* *Misconception 2:* "نقطة الـ API هي مجرد اختصار مباشر لاستعلام الداتا بيز (Database Shortcut)." -> *الواقع:* الـ Backend هو المسؤول عن تطبيق قوانين العمل وضمان صحة التحولات قبل أي تخزين.
* *Misconception 3:* "المصادقة (AuthN) تعني أن المستخدم يحق له تنفيذ الإجراء." -> *الواقع:* المصادقة تثبت الهوية فقط، بينما التفويض (AuthZ) يقرر هل يحق لهذه الهوية التعديل على هذا المورد المحدّد.

## Failure / Edge Cases
* **توكن منتهي أو مفقود:**
  `Request` ← `فحص المصادقة AuthN` ← `إرجاع 401 Unauthorized`.
* **كابتن موثق يغير توصيل كابتن آخر:**
  `فحص AuthN بنجاح` ← `فحص التفويض AuthZ والملكية` ← `فشل الملكية` ← `إرجاع 403 Forbidden`.
* **طلب أوردر غير موجود بالأساس:**
  `البحث بالداتا بيز` ← `غير موجود` ← `إرجاع 404 Not Found`.
* **مخالفة قاعدة عمل (مثل طلب وجبة غير متاحة):**
  `فحص منطق العمل` ← `مخالفة` ← `إرجاع 400 / 422 حسب اتفاقية الكورس`.
* **انقطاع غير متوقع في الداتا بيز:**
  `خطأ سيرفر غير معالج` ← `إرجاع 500 Internal Server Error`.

## Explain Back
* اشرح بأسلوبك الخاص الفرق بين المصادقة (AuthN) والتفويض (AuthZ)، ودورة الحياة المفاهيمية للطلب داخل الـ Backend من لحظة وصوله حتى خروج الاستجابة.

## Understanding Checklist
* أستطيع شرح التمييز بين مسؤوليات تطبيق العميل ومسؤوليات الـ Backend.
* أستطيع شرح النموذج المفاهيمي للطلب والاستجابة عبر بروتوكول HTTP.
* أستطيع التعرف على أجزاء الـ HTTP Request الرئيسية (Method, Path, Headers, Body).
* أستطيع التفريق الصريح بين المصادقة AuthN (`401`) والتفويض AuthZ (`403`).
* أستطيع توضيح لماذا يعتبر فحص الـ Backend حتمياً حتى لو توفر فحص بالواجهة.
* أستطيع شرح مفهوم أن طلب الـ API قد يطلق عدة إجراءات تجارية داخلية.
* أستطيع استخدام دلالات أخطاء HTTP بشكل منطقي متسق.

## Exit Assessment
عند إعطائك إجراء عميل بالواجهة (مثل "تأكيد الطلب" أو "تحديث حالة التوصيل"):
1. تتبع مسار الطلب مفاهيمياً من الواجهة وحتى الـ Backend والاستجابة الختامية.
2. فرّق بين خطوة فحص هوية الداعي (AuthN) وخطوة فحص ملكيته وصلاحيته للمورد (AuthZ).
3. اشرح لماذا يُمنع اعتماد السعر المبعوث من الواجهة الأمامية بالطلب.
4. استخرج 3 أخطاء أمنية ودلالية من تصميم API مبعوث من الـ AI (مثل غياب AuthZ، الاعتماد على بيانات السعر المبعوثة، أو إرجاع `200 OK` عند فشل العملية).

## Exit Target
القدرة الملموسة على تتبع دورة الحياة المفاهيمية للطلب، والتفريق الصريح بين المصادقة والتفويض والتحقق، وتوضيح دور منطق العمل وعمليات التخزين، واستخدام دلالات HTTP بوعي، وتحديد خطوات الأمان والتحقق المفقودة في تصاميم الـ API الصادرة من الـ AI بنجاح.

## PASS Criteria
يتأهل المتعلم للاجتياز فقط إذا كان قادراً على:
1. شرح مسؤوليات العميل مقابل الـ Backend.
2. شرح نموذج Request/Response الأساسي لـ HTTP.
3. تحديد المكونات الرئيسية لـ HTTP Request.
4. التفريق الصريح بين المصادقة AuthN والتفويض AuthZ ضرباً أمثلة بـ HDS.
5. توضيح سبب حتمية فحص الـ Backend وعدم الاكتفاء بفحوصات الواجهة.
6. تتبع دورة الحياة المفاهيمية للطلب (Routing, AuthN, AuthZ, Validation, Business Logic, DB Ops, Response).
7. استخدام دلالات أخطاء HTTP بشكل متسق ومعلل.
8. توضيح أن طلب الـ API قد يتضمن عدة إجراءات تجارية داخلية.
9. اكتشاف أخطاء الأمان والتحقق في تصميم API مبعوث من الـ AI.
10. اجتياز خطوة الشرح المفاهيمي (Explain Back) بنجاح.

## NOT YET Criteria
* يخلط بين المصادقة AuthN والتفويض AuthZ.
* يعتقد أن فحوصات الواجهة الأمامية كافية أمنياً بدون فحوصات بالـ Backend.
* يثق في بيانات الأسعار المبعوثة من العميل.
* لا يستطيع تتبع مسار الطلب لما بعد الواجهة.
* يعامل أكواد استجابة HTTP كأرقام عشوائية لا دلالة لها.
* يفشل في اكتشاف غياب التفويض AuthZ في تصميم صادر من الـ AI.
* يفشل في خطوة الـ Explain Back.

## Minimum vs Deeper Understanding

### Minimum — Required for PASS (الحد الأدنى للاجتياز):
* مسؤوليات Client vs Backend.
* Request/Response عبر HTTP وأجزاء الطلب.
* المصادقة AuthN مقابل التفويض AuthZ والتحقق Validation.
* المسار المفاهيمي لـ Request Lifecycle.
* دلالات استجابات HTTP والأخطاء الشائعة.
* مبدأ "الطلب ≠ العملية التجارية الواحدة".

### Deeper — Learn Later (مفاهيم متقدمة تتعلمها لاحقاً):
* تفاصيل وتشفير رموز الـ JWT الداخلية.
* بروتوكولات gRPC و HTTP/2 و HTTP/3 multiplexing.
* خوارزميات تحديد معدل الطلبات (Rate Limiting token bucket).
* إعدادات ورسوومات الـ API Gateways والبنية التحتية.
* كتابة الـ Syntax المباشر لراوترات أطر العمل (Express/Nest/Fastify).
